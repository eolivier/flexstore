# Database convention

Rules collected from the user's feedback for the database schema (`backend/migrations/src/main/resources/db/migration`). Apply them to every new migration and check them in reviews. When an existing table breaks them, point it out; bringing it in line is a refactoring of its own (a new migration, never a change to a migration already applied).

The JPA side of the tables (entities, timestamps) is described in the `infrastructure-convention` skill.

## 1. Every table has a primary key named `id`, a foreign key is prefixed with its table

Every table has a primary key, on a single technical column that may be called `id`. A table never goes without a primary key, and its key is never a business value (a token hash, an email, a code) nor a composite of other columns: such a value gets a `UNIQUE` constraint next to the key.

A column that references another table (a foreign key) is named after that table, with the suffix `_id`: `user_id` references `"user"(id)`, `cart_id` references `cart(id)`. When a table references the same table several times, or for a given role, a qualifier goes in front: `delivery_address_id` and `billing_address_id` reference `address(id)`.

Avoid:

```sql
CREATE TABLE email_verification (
    token_hash VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL REFERENCES "user"(id),
    ...
);
```

Prefer:

```sql
CREATE TABLE email_verification (
    id VARCHAR(50) PRIMARY KEY,
    token_hash VARCHAR(64) NOT NULL UNIQUE,
    expires_at TIMESTAMP WITH TIME ZONE NOT NULL,
    ...
);

-- The user has an email verification: the user references it, not the other way round
ALTER TABLE "user" ADD COLUMN email_verification_id VARCHAR(50) REFERENCES email_verification(id);
```

Why: every row is designated the same way, by its `id`, whatever the table; a foreign key tells by its name which table it points to; a business value can change or stop being unique, while the key of the row stays.

Details:
- The foreign key goes in the table of the row that has or uses the other one: the user has an email verification (`"user".email_verification_id`), an order has a delivery address (`customer_order.delivery_address_id`). The referenced row does not point back to its owner (no `email_verification.user_id`).
- The ids are generated by the application (`Identity.nextId()`), as text (`VARCHAR(50)`), like the existing tables.

## 2. A reference to another table is a foreign key

When a row uses a row of another table (the address of an order, the user of a cart), it holds the `id` of that row in a foreign key column (`REFERENCES`), never a copy of its columns.

Avoid:

```sql
CREATE TABLE customer_order (
    id VARCHAR(50) PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL REFERENCES "user"(id),
    delivery_street VARCHAR(255) NOT NULL,
    delivery_postal_code VARCHAR(20) NOT NULL,
    delivery_city VARCHAR(100) NOT NULL,
    ...
);
```

Prefer:

```sql
-- The recipient of an address may differ from the user: its own names, no user_id
CREATE TABLE address (
    id VARCHAR(50) PRIMARY KEY,
    first_name VARCHAR(255) NOT NULL,
    last_name VARCHAR(255) NOT NULL,
    company_name VARCHAR(255),
    street VARCHAR(255) NOT NULL,
    ...
);

-- The addresses of a user, in the order they were given
CREATE TABLE user_address (
    id VARCHAR(50) PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
    address_id VARCHAR(50) NOT NULL REFERENCES address(id),
    position INT NOT NULL,
    UNIQUE (user_id, address_id)
);

CREATE TABLE customer_order (
    id VARCHAR(50) PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL REFERENCES "user"(id),
    delivery_address_id VARCHAR(50) NOT NULL REFERENCES address(id),
    billing_address_id VARCHAR(50) NOT NULL REFERENCES address(id),
    ...
);
```

Why: the data is stored once, the database guarantees that the referenced row exists, and a row that is still referenced cannot be deleted by mistake.

Details:
- Choose the `ON DELETE` behaviour on purpose: `CASCADE` when the row cannot exist without the referenced one (the lines of an order), the default (`RESTRICT`) when the referenced row must be kept while it is used (an address used by an order).
- Index the foreign key columns used to search (`CREATE INDEX customer_order_user_id_idx ON customer_order(user_id)`).
- A foreign key is not a shortcut for values that can differ from the referenced row: a row that has its own values stores them in its own columns. The recipient of an address (`first_name`, `last_name`, `company_name`) can be someone other than the user (a gift, a company), so the address holds it and does not take it from `user_id`.
- A row that can be used by several others (an address used by a user and by their orders) does not point to one of them: the link goes in the tables that use it (`customer_order.delivery_address_id`), or in a link table when it is many to many (`user_address`).
- A copy is only kept when the business needs the value at a given time and the referenced row can change: say why in a comment of the migration (the name and the price of a product in an order line).

## 3. Mandatory columns are `NOT NULL`, old rows are migrated

A column that the business says is always filled is `NOT NULL`, like the non-null property of the domain (see principle 9 of the `fluent-code-reading-semantic` skill). When the column is added to a table that already has rows, the migration fills it for them (from the data at hand), then sets `NOT NULL`, rather than leaving the column nullable for the old rows.

```sql
ALTER TABLE "user" ADD COLUMN first_name VARCHAR(255);
UPDATE "user" SET first_name = split_part(btrim(name), ' ', 1);
ALTER TABLE "user" ALTER COLUMN first_name SET NOT NULL;
```

Why: a nullable column for old data makes every reader of the table, and the domain type, handle a case that new data never has.

Details:
- When some old rows cannot be filled, say in the migration what is done with them and why, and point it out in the pull request.

## 4. A schema change updates the physical data model

The physical data model of the database (MPD) is kept in two forms, updated together:
- `docs/database.md`: the source, a Mermaid `erDiagram` (a text that GitHub and most editors render as an image), with notes;
- `docs/database.png`: the image of the diagram (PNG or JPG), generated from the Markdown by `docs/render-database-diagram.sh`, for the readers and tools that do not render Mermaid. The Markdown shows it too.

Every migration that changes the schema (a table, a column, a type, a key, a constraint) updates both in the same pull request.

How to apply:
- Add, rename or remove the table or the column in the diagram, with its type, `PK`, `FK` or `UK`, and a comment for what is not obvious (a nullable column, an enumeration such as `PENDING` / `PAID`).
- Draw the relation of a new foreign key with its cardinality (`||--o{`, `|o--o|`...), labelled with the column that holds it.
- Update the version of the last migration written at the top of the document.
- Regenerate the image with `docs/render-database-diagram.sh`, and look at it: it must render, and be readable.
- Place the tables so that the links do not cross (or as little as possible): the diagram is laid out from left to right by ELK (`"layout": "elk"` and `direction LR`); write a relation from the table that holds the foreign key when the referenced table should be on the right, declare the tables in reading order, and compare with another layout when links still cross.
- Keep the colors clear and readable: a light theme (light backgrounds, dark text with a strong contrast, visible lines), set once in the `%%{init: ...}%%` line of the diagram; no dark or saturated backgrounds, no light text.

Why: the diagram gives at a glance the tables, their keys and their relations, which the migrations only give one change at a time; a diagram that is not updated with the schema misleads more than it helps.

## 5. No circular dependency between tables

The foreign keys never form a cycle: a table never references, directly or through other tables, a table that references it. The tables can always be ordered so that each one only references the tables before it.

Avoid:

```sql
-- The user references their last email verification, and the verification references its user
ALTER TABLE "user" ADD COLUMN email_verification_id VARCHAR(50) REFERENCES email_verification(id);
ALTER TABLE email_verification ADD COLUMN user_id VARCHAR(50) REFERENCES "user"(id);
```

Prefer:

```sql
-- Only the owner references what it has (see principle 2)
ALTER TABLE "user" ADD COLUMN email_verification_id VARCHAR(50) REFERENCES email_verification(id);
```

Why: with a cycle, no row can be inserted or deleted first without a nullable column or a deferred constraint, the deletions in cascade loop, and the data of a table cannot be loaded, copied or emptied on its own; the cycle also hides which table owns the other.

How to apply:
- Before adding a foreign key, follow the arrows of the physical data model (`docs/database.md`, principle 4) from the referenced table: the new key must not lead back to its own table.
- A relation in both directions keeps a single foreign key, held by the owner (principle 2); the other direction is a query, not a column.
- A table that must reference rows of its own kind (a hierarchy) is the only accepted self-reference, with a nullable key, and is said in a comment of the migration.
